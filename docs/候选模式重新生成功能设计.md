## 🎯 背景和问题

### 当前实现的问题

在之前的设计中，重新生成功能分为两种模式：

1. **覆盖式重新生成**（仅最后一条消息）：直接替换原消息内容
2. **分支式重新生成**（所有消息）：创建新会话，探索不同方向

**存在的痛点**：

- **覆盖式的问题**：
  - 直接替换导致原内容丢失，无法对比
  - 无法生成多个版本进行择优
  - 不适合"生成几个答案对比选择"的场景

- **分支式的问题**：
  - 太"重"，创建新session，适合"探索不同方向"
  - 不适合"快速对比同一问题的多个答案"的轻量场景

- **用户需求**：
  - 想要多次生成，对比几个答案
  - 选择最优的，或总结融合多个答案
  - 不想每次都创建分支（太重）

### 核心矛盾

需要一个**介于覆盖和分支之间的轻量级机制**：
- 比覆盖灵活（可以生成多个、对比）
- 比分支轻量（不创建新会话，临时对比）

---

## 💡 解决方案：候选模式

### 核心思路

重新生成时，进入**候选模式**：
- 原消息变成"候选0"（锚点消息）
- 新生成的消息变成"候选1、2、3..."
- 所有候选以**横向卡片**形式展示
- 用户可以生成多个、对比、标记喜欢的
- 发送新消息时，采用选中的候选，其他删除

### 设计原则

1. **轻量化**：候选是临时的，最终只保留一个
2. **可视化**：所有候选一目了然，不隐藏
3. **灵活性**：可以生成任意多个，随时删除、对比
4. **和分支区分**：
   - 候选模式 = 快速对比同一问题的多个答案
   - 分支模式 = 探索不同的对话路径

**UI变化**：

### 2. 候选模式下的操作

**每个Card的工具栏**：
- **复制**：复制该候选内容
- **🔄 重新生成**：新增一个候选（不覆盖）
- **🌿 基于此创建分支**：基于该候选创建新会话
- **移除**（仅非Card 0）：从候选池删除该候选

**上下文标记**：
- 右上角显示：✓（已选）或空白（未选）
- 边框颜色：蓝色（已选）或灰色（未选）
- 单选：同时只能有一个候选作为上下文
- 生成中的候选不可设为上下文

**中止按钮**：
- 每个生成中的card右上角：小型[⏹️]按钮（中止该候选）
- 输入框的中止按钮：中止当前会话所有流式（包括所有候选）

### 3. 候选Card的布局

**横向排列**：
- 所有card横向排列（左到右）
- 自动换行（每行2-3个，根据屏幕宽度）
- 横向滚动支持

**Card样式**：
- `max-height`: 一屏高度（避免过长）
- 内部滚动：超过高度时，card内部可滚动
- 最小宽度：300px
- 最大宽度：600px（自适应）

### 4. 退出候选模式

**触发条件**：

1. **发送新消息**：
   ```
   用户输入新消息 → 弹出确认：
   
   "将使用 Card 2 作为上下文继续对话
    其他候选将被删除，此操作不可撤销"
   
   [确认发送] [取消]
   ```
   
   确认后：
   - 采用选中的候选（覆盖锚点消息内容）
   - 删除其他候选
   - 退出候选模式
   - 发送新消息

2. **删除到只剩1个**：
   - 自动退出候选模式
   - 恢复普通消息样式

### 5. 特殊情况

**Card 0（锚点消息）的特殊性**：
- 不显示"移除"按钮（不可删除）
- 保持消息ID不变（用于分支引用）
- 采用其他候选时，内容被覆盖

**生成中能否发送**：
- 允许发送
- 自动中止所有生成中的候选
- 弹出确认提示

## 🗄️ 数据库设计

### 1. messages 表字段扩展

```sql
ALTER TABLE messages ADD COLUMN candidate_group_id TEXT;
ALTER TABLE messages ADD COLUMN is_anchor_message INTEGER DEFAULT 0;
ALTER TABLE messages ADD COLUMN is_context_candidate INTEGER DEFAULT 0;
```

**字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `candidate_group_id` | TEXT | 候选组ID，`NULL`表示正式消息 |
| `is_anchor_message` | INTEGER | 是否是锚点消息（原始消息），`1`=是 |
| `is_context_candidate` | INTEGER | 是否是上下文候选，`1`=是 |
| `created_at` | INTEGER | 创建时间（用于候选排序） |

**查询逻辑**：

```sql
-- 查询正式消息（非候选）
SELECT * FROM messages 
WHERE session_id = ? AND candidate_group_id IS NULL
ORDER BY created_at

-- 查询某个候选组的所有候选
SELECT * FROM messages 
WHERE candidate_group_id = ?
ORDER BY created_at
```

### 2. sessions 表字段扩展（用于分支）

```sql
ALTER TABLE sessions ADD COLUMN fork_from_candidate_id TEXT;
```

**字段说明**：

| 字段 | 说明 |
|------|------|
| `fork_from_candidate_id` | 如果从候选模式创建分支，记录候选ID |

**用途**：
- 候选模式下创建分支时，分叉点提前到user消息
- 但记录基于哪个候选创建，用于会话总览显示

### 1. 进入候选模式

**前端流程**：

```typescript
// MessageItem.vue - 点击"重新生成"
async function handleRegenerate() {
  // 调用后端接口，创建候选组
  await chatStore.regenerateWithCandidates(message.id)
  
  // 后端会自动：
  // 1. 标记原消息为候选模式
  // 2. 创建新候选并开始生成
  // 3. 通过流式返回新候选内容
}
```

**后端实现**：

```typescript
// router.ts
ipc.handle('messages:regenerateWithCandidates', async ({ messageId }) => {
  // 1. 获取原消息
  const originalMessage = getMessage(messageId)
  
  // 2. 生成候选组ID
  const groupId = `candidate-${Date.now()}-${randomId()}`
  
  // 3. 标记原消息为候选模式
  updateMessage(originalMessage.id, {
    candidateGroupId: groupId,
    isAnchorMessage: true,
    isContextCandidate: true
  })
  
  // 4. 获取父user消息
  const userMessage = getParentUserMessage(messageId)
  
  // 5. 创建新候选
  const newCandidate = createAssistantMessage({
    sessionId: originalMessage.sessionId,
    selectedModel: originalMessage.selectedModel,
    status: 'pending',
    candidateGroupId: groupId,
    isAnchorMessage: false,
    isContextCandidate: false
  })
  
  // 6. 准备对话历史（排除候选消息）
  const historyMessages = getDisplayMessages(originalMessage.sessionId)
    .filter(m => !m.candidateGroupId && m.id !== messageId)
  
  // 7. 开始流式生成
  await executeChat({
    sessionId: originalMessage.sessionId,
    messages: prepareDialogMessages(historyMessages, userMessage.content),
    selectedModel: originalMessage.selectedModel,
    assistantMessageId: newCandidate.id,
    window,
    abortSignal
  })
  
  return { ok: true, groupId, candidateId: newCandidate.id }
})
```

### 4. 删除候选

**前端**：

```typescript
async function deleteCandidate(candidateId: string, groupId: string) {
  await window.ipc('messages:deleteCandidate', {
    candidateId,
    groupId
  })
  
  // 后端返回是否需要退出候选模式
  // 如果只剩1个，前端自动切换渲染模式
}
```

**后端**：

```typescript
ipc.handle('messages:deleteCandidate', async ({ candidateId, groupId }) => {
  const candidate = getMessage(candidateId)
  
  // 不允许删除锚点消息
  if (candidate.isAnchorMessage) {
    throw new Error('不能删除锚点消息')
  }
  
  // 物理删除
  db.prepare('DELETE FROM messages WHERE id = ?').run(candidateId)
  
  // 检查剩余候选数量
  const remaining = db.prepare(
    'SELECT COUNT(*) as count FROM messages WHERE candidate_group_id = ?'
  ).get(groupId)
  
  if (remaining.count === 1) {
    // 只剩1个，退出候选模式
    const anchorMessage = db.prepare(
      'SELECT * FROM messages WHERE candidate_group_id = ? AND is_anchor_message = 1'
    ).get(groupId)
    
    if (anchorMessage) {
      // 恢复为普通消息
      db.prepare(`
        UPDATE messages 
        SET candidate_group_id = NULL, 
            is_anchor_message = NULL, 
            is_context_candidate = NULL
        WHERE id = ?
      `).run(anchorMessage.id)
    }
    
    return { ok: true, exitCandidateMode: true }
  }
  
  // 如果删除的是上下文候选，自动设置第一个剩余候选为上下文
  if (candidate.isContextCandidate) {
    const firstRemaining = db.prepare(
      'SELECT * FROM messages WHERE candidate_group_id = ? ORDER BY created_at LIMIT 1'
    ).get(groupId)
    
    if (firstRemaining) {
      db.prepare(
        'UPDATE messages SET is_context_candidate = 1 WHERE id = ?'
      ).run(firstRemaining.id)
    }
  }
  
  return { ok: true, exitCandidateMode: false }
})
```

```typescript
// useChatStore.ts - 发送消息前检查
async function sendMessage(content: string) {
  // 检查是否在候选模式
  const lastMessage = messages.value[messages.value.length - 1]
  
  if (lastMessage?.candidateGroupId) {

  // ...
}
```

**后端**：

```typescript
ipc.handle('messages:adoptCandidate', async ({ groupId }) => {
  // 1. 找到锚点消息
  const anchorMessage = db.prepare(
    'SELECT * FROM messages WHERE candidate_group_id = ? AND is_anchor_message = 1'
  ).get(groupId)
  
  if (!anchorMessage) {
    throw new Error('找不到锚点消息')
  }
  
  // 2. 找到上下文候选
  const contextCandidate = db.prepare(
    'SELECT * FROM messages WHERE candidate_group_id = ? AND is_context_candidate = 1'
  ).get(groupId)
  
  if (!contextCandidate) {
    throw new Error('找不到上下文候选')
  }
  
  // 3. 用上下文候选的内容覆盖锚点消息
  db.prepare(`
    UPDATE messages 
    SET 
      content = ?,
      selected_model = ?,
      updated_at = ?,
      candidate_group_id = NULL,
      is_anchor_message = NULL,
      is_context_candidate = NULL
    WHERE id = ?
  `).run(
    contextCandidate.content,
    contextCandidate.selectedModel,
    Date.now(),
    anchorMessage.id
  )
  
  // 4. 删除所有候选（包括被采用的）
  db.prepare('DELETE FROM messages WHERE candidate_group_id = ?').run(groupId)
  
  // 5. 更新会话时间
  touchSession(anchorMessage.sessionId)
  
  return { ok: true }
})
```

**关键设计**：分叉点提前到user消息，避免候选被删除导致引用失效

**前端**：

```typescript
}
```

**后端**：

```typescript
ipc.handle('sessions:createBranchFromCandidate', async ({ 
  parentSessionId, 
  candidateId 
}) => {
  // 1. 获取候选消息
  const candidate = getMessage(candidateId)
  const groupId = candidate.candidateGroupId
  
  // 2. 找到锚点消息
  const anchorMessage = db.prepare(
    'SELECT * FROM messages WHERE candidate_group_id = ? AND is_anchor_message = 1'
  ).get(groupId)
  
  if (!anchorMessage) {
    throw new Error('找不到锚点消息')
  }
  
  // 3. 找到对应的user消息（锚点的parent）
  const userMessage = db.prepare(
    'SELECT * FROM messages WHERE session_id = ? AND id = ?'
  ).get(anchorMessage.sessionId, anchorMessage.parentId)
  
  if (!userMessage || userMessage.role !== 'user') {
    throw new Error('找不到对应的user消息')
  }
  
  // 4. 创建分支会话（分叉点=user消息）
  const rootSessionId = getCurrentRootSessionId(parentSessionId)
  const parentSession = getSession(parentSessionId)
  
  const newSession = createSession({
    title: `${parentSession.title} - 分支`,
    selectedModel: parentSession.selectedModel,
    scenarioId: parentSession.scenarioId,
    rootSessionId: rootSessionId || parentSessionId,
    parentSessionId: parentSessionId,
    forkFromMessageId: userMessage.id,        // 分叉点=user消息
    forkFromCandidateId: candidateId          // 记录基于哪个候选
  })
  
  // 5. 复制消息到分叉点（user消息）
  copyMessagesToForkPoint(parentSessionId, userMessage.id, newSession.id)
  
  // 6. 在新会话中创建assistant消息（使用候选内容）
  const copiedUserMessage = db.prepare(
    'SELECT * FROM messages WHERE session_id = ? ORDER BY created_at DESC LIMIT 1'
  ).get(newSession.id)
  
  const newAssistantMessage = createMessage({
    sessionId: newSession.id,
    role: 'assistant',
    content: candidate.content,
    selectedModel: candidate.selectedModel,
    parentId: copiedUserMessage.id,
    copiedFromMessageId: candidateId,
    isShared: false,
    status: 'success'
  })
  
  // 7. 更新会话的 first_new_message_id
  updateSession(newSession.id, {
    firstNewMessageId: newAssistantMessage.id
  })
  
  return newSession
})
```

### 7. 刷新后恢复候选模式

**前端加载逻辑**：

```typescript
// useChatStore.ts - 加载消息时
async function loadMessages(sessionId: string) {
  const messages = await window.ipc('messages:getDisplayMessages', { sessionId })
  
  // 检查最后一条消息是否在候选模式
  const lastMessage = messages[messages.length - 1]
  
  if (lastMessage?.candidateGroupId) {
    // 加载该候选组的所有候选
    const candidates = await window.ipc('messages:getCandidates', {
      groupId: lastMessage.candidateGroupId
    })
    
    // 存储到候选状态
    candidateGroups.value.set(sessionId, {
      groupId: lastMessage.candidateGroupId,
      candidates,
      contextCandidateId: candidates.find(c => c.isContextCandidate)?.id
    })
  }
  
  return messages
}
```

**后端接口**：

```typescript
ipc.handle('messages:getCandidates', async ({ groupId }) => {
  const candidates = db.prepare(`
    SELECT * FROM messages 
    WHERE candidate_group_id = ? 
    ORDER BY 
      CASE WHEN is_anchor_message = 1 THEN 0 ELSE 1 END,
      created_at
  `).all(groupId)
  
  return candidates
})
```

## 🔍 边界情况处理

### 1. 并发生成中发送新消息

**场景**：
```
[Card 0✓] [Card 1 - 生成中⏳] [Card 2 - 生成中⏳]
用户点击发送新消息
```

**处理**：
1. 自动中止所有生成中的候选
2. 弹出确认："将中止2个生成中的候选并继续对话"
3. 确认后采用上下文候选，发送新消息

### 2. 删除上下文候选

**场景**：
```
[Card 0✓] [Card 1] [Card 2]
删除 Card 0（上下文）
```

**处理**：
- 禁止删除 Card 0（锚点消息）
- 如果是其他上下文候选被删除，自动将第一个剩余候选设为上下文

### 3. 候选模式下切换会话

**场景**：
```
会话A：候选模式 [Card 0✓, Card 1, Card 2]
切换到会话B
再切回会话A
```

**处理**：
- 前端缓存候选状态（`Map<sessionId, CandidateGroup>`）
- 切回时从缓存恢复
- 缓存失效时从数据库重新加载

### 4. 候选被删除后的分支引用

**场景**：
```
在Card 2上创建分支
原会话采用Card 0，Card 2被删除
分支的 forkFromCandidateId 指向已删除的消息
```

**处理**：
- `forkFromMessageId` 指向user消息（永远不会被删除）
- `forkFromCandidateId` 用于显示"基于哪个候选"
- 会话总览显示时，从分支的副本中获取候选内容

### 5. 锚点消息被软删除

**场景**：
```
候选模式采用某个候选后，退出候选模式
用户对普通消息执行删除（软删除）
分支引用该消息
```

**处理**：
- 软删除不影响分支引用（消息ID仍然存在）
- 分支在创建时已复制内容，不依赖原消息内容
- 会话总览显示时，如果原消息被删除，显示"消息已删除"，但分支内容完整

## ✅ 总结

### 核心优势

1. **轻量对比**：不创建分支，快速生成多个版本
2. **可视化强**：横向卡片，所有候选一目了然
3. **灵活性高**：可以生成任意多个，随时删除、对比
4. **不破坏引用**：采用候选覆盖锚点，保持消息ID稳定
5. **状态可恢复**：刷新后自动恢复候选模式

### 与分支功能的区分

| 特性 | 候选模式 | 分支模式 |
|------|---------|---------|
| **用途** | 快速对比同一问题的多个答案 | 探索不同的对话路径 |
| **持久性** | 临时的，最终只保留一个 | 永久保存，可随时切换 |
| **可见性** | 在当前消息位置横向展开 | 在会话列表中平级显示 |
| **后续对话** | 采用一个后继续 | 每个分支独立发展 |
| **心智模型** | "我想要更好的答案" | "我想试试另一个方向" |

这个设计既满足了轻量对比的需求，又保持了和分支功能的清晰区分，为用户提供了完整的消息重新生成体验。
